3.2.2 Diagram Flowchart Alur Sistem Digital (sNaps)

Pemetaan logika komputasi terotomatisasi transaksi C2C dan interaksi komunitas pada aplikasi sNaps SMKN 8 Semarang.

flowchart TD
    Start([Mulai: Siswa Membuka Aplikasi sNaps]) --> CheckAuth{Apakah Token Sesi Login Aktif?}
    CheckAuth -- Tidak --> InputNIS[Input NIS & Password Siswa]
    InputNIS --> ValidateRegistry[(Validasi ke Tabel student_registry)]
    ValidateRegistry --> CheckNISValid{Apakah NIS Terdaftar & Aktif?}
    CheckNISValid -- Tidak --> ShowAlertAuth[Tampilkan Peringatan: 'NIS Tidak Terdaftar di SMKN 8'] --> InputNIS
    CheckNISValid -- Ya --> CreateSession[Terbitkan Sesi JWT & Muat Profil Siswa]
    
    CheckAuth -- Ya --> LoadHome[Buka Layar Beranda: Feed Komunitas & Marketplace]
    CreateSession --> LoadHome

    LoadHome --> UserNavChoice{Pilih Aktivitas Siswa}

    %% JALUR PENJUAL
    UserNavChoice -- Jual Produk / Unjuk Karya --> OpenCreatePost[Buka Formulir Pembuatan Listing Produk]
    OpenCreatePost --> FillProductData[Input Judul, Deskripsi, Kategori Jurusan, Foto, Harga, Stok]
    FillProductData --> ValidateInput{Validasi Input Lengkap?}
    ValidateInput -- Tidak --> ShowErrorForm[Tampilkan Pesan Error Validasi Form] --> FillProductData
    ValidateInput -- Ya --> InsertProductDB[(Simpan Record Baru ke Tabel market_posts)]
    InsertProductDB --> PostBroadcast[Produk Tayang Secara Publik di Feed] --> EndSellerWait([Selesai: Menunggu Pembeli])

    %% JALUR PEMBELI
    UserNavChoice -- Beli Produk Vokasi --> BrowseMarket[Jelajah Katalog & Filter Kategori: PPLG / DKV / Kuliner]
    BrowseMarket --> OpenDetail[Buka Halaman Detail Produk & Profil Penjual]
    OpenDetail --> CheckAvailableStock{Cek Database: Apakah Stok > 0?}
    CheckAvailableStock -- Habis (0) --> ShowEmptyState[Tombol Beli Dinonaktifkan: 'Stok Habis'] --> BrowseMarket
    CheckAvailableStock -- Tersedia --> TapBuy[Tekan Tombol 'Beli Sekarang']
    
    TapBuy --> OpenCheckoutSheet[Sistem Membuka Lembar Checkout COD]
    OpenCheckoutSheet --> LoadMeetingPoints[(Query Lokasi Aktif dari school_meeting_points)]
    LoadMeetingPoints --> SelectPoint[Pembeli Memilih Titik Temu: Gazebo / Kantin / Lab]
    SelectPoint --> InputBuyerNote[Pembeli Menulis Catatan Jam COD Istirahat]
    InputBuyerNote --> TapConfirmOrder[Tekan 'Konfirmasi Pesanan']

    TapConfirmOrder --> AtomicTxBegin[(Mulai Transaksi Database Atomik)]
    AtomicTxBegin --> LockStockRow{Kunci Baris & Validasi Stok Akhir}
    LockStockRow -- Stok Habis Dibeli Siswa Lain --> RollbackTx[Batalkan Transaksi & Tampilkan Alert] --> BrowseMarket
    LockStockRow -- Stok Valid --> InsertOrder[(Insert ke Tabel orders: Status PENDING)]
    InsertOrder --> DeductStockDB[(Update: Kurangi Kuantitas Stok di market_posts)]
    DeductStockDB --> AtomicTxCommit[(Commit Transaksi Database)]

    AtomicTxCommit --> TriggerPushNotif[Kirim Push Notification Masuk ke HP Siswa Penjual]
    TriggerPushNotif --> GenerateDigitalReceipt[Terbitkan Bukti Pesanan Digital dengan Kode Transaksi Unik]
    GenerateDigitalReceipt --> ShowSuccessModal[Tampilkan Modal Sukses Checkout ke Pembeli]
    
    ShowSuccessModal --> MeetPhysicalCOD[Kedua Siswa Bertemu di Titik Temu Sekolah Sesuai Catatan]
    MeetPhysicalCOD --> CompleteVerification[Pembeli Memeriksa Barang & Membayar Tunai]
    CompleteVerification --> TapOrderDone[Siswa Menekan 'Pesanan Selesai' di Aplikasi]
    TapOrderDone --> UpdateOrderStatusDB[(Update Status Pesanan: COMPLETED di Tabel orders)]
    UpdateOrderStatusDB --> EndFinish([Selesai: Transaksi Berhasil])

Penjelasan Tahapan Krusial Sistem:

  1. Validasi NIS Dua Lapis (Two-Tier Auth): Aplikasi memeriksa keabsahan nomor induk ke student_registry sekolah sebelum menerbitkan sesi JWT dan profil pengguna.
  2. Pencegahan Race Condition & Concurrency-Safe: Dua siswa yang menekan tombol beli secara bersamaan pada barang bersisa 1 unit tidak akan menyebabkan stok negatif karena query menerapkan transaksi atomik penguncian baris (SELECT FOR UPDATE).
  3. Master Data Titik Temu Resmi Sekolah: Lokasi COD wajib dipilih dari entitas school_meeting_points (Gazebo Utama, Kantin Pusat, Lab PPLG) untuk mengeliminasi friksi salah tempat janji temu.
  4. Penerbitan Bukti Digital Instan: Nota digital tersimpan otomatis di akun kedua belah pihak sebagai rujukan valid saat serah terima barang secara fisik.

3.2.1 Diagram Flowchart Alur Manual (Konvensional)

Pemetaan alur transaksi konvensional siswa sebelum menggunakan sistem aplikasi sNaps.

flowchart TD
    NodeStart([Mulai: Siswa Ingin Menjual Produk/Karya]) --> NodeUpload[Siswa Mengambil Foto & Membuat Teks Promosi Manual]
    NodeUpload --> NodeBroadcast[Unggah ke Status WhatsApp & Grup Angkatan]
    NodeBroadcast --> NodeWait[Menunggu Respon Chat Calon Pembeli]
    
    NodeWait --> NodeConditionResponse{Apakah Ada Siswa yang Membalas Chat?}
    NodeConditionResponse -- Tidak (Tenggelam) --> NodeExpired[Postingan Hilang dalam 24 Jam / Tanpa Hasil Penjualan]
    NodeExpired --> NodeEndCancel([Selesai / Transaksi Batal])
    
    NodeConditionResponse -- Ya --> NodeNegotiate[Tanya Jawab Manual via DM: Tanya Ketersediaan Stok & Nego Harga]
    NodeNegotiate --> NodeConditionDeal{Apakah Tercapai Kesepakatan Harga?}
    NodeConditionDeal -- Tidak Sepakat --> NodeEndCancel
    
    NodeConditionDeal -- Sepakat --> NodeAppointment[Menentukan Waktu & Janji Temu Lokasi via Chat Teks]
    NodeAppointment --> NodeRisk[Rawan Miskomunikasi: Siswa Salah Lokasi Lantai / Jam Bentrok / Ghosting]
    
    NodeRisk --> NodeMeet[Kedua Siswa Bertemu Secara Fisik di Area Sekolah]
    NodeMeet --> NodeInspect[Pembeli Memeriksa Fisik Barang Secara Langsung]
    NodeInspect --> NodePay[Pembeli Menyerahkan Uang Tunai / Cash]
    NodePay --> NodeReceipt[Penjual Menghitung Kembalian & Menyerahkan Barang Fisik]
    NodeReceipt --> NodeManualRecord[Penjual Mencatat Penjualan di Buku Catatan Kertas / Catatan HP Pribadi]
    NodeManualRecord --> NodeEndSuccess([Selesai: Transaksi Manual Berhasil])

Analisis Titik Kritis Alur Manual:

  • Chat Tenggelam (Message Ephemerality): Postingan status WhatsApp hilang dalam 24 jam dan sering terkubur ratusan chat obrolan kelas lainnya.
  • Ketidakpastian Ketersediaan Barang (No Live Stock): Calon pembeli harus menanyakan stok berulang kali via DM pribadi.
  • Resiko Janji Temu Mengambang (Meeting Friction): Koordinasi tempat bertemu sering memicu salah lokasi atau salah waktu karena instruksi teks bebas yang ambigu.
  • Nir-Pencatatan Finansial Baku: Tidak ada rekapitulasi penjualan otomatis yang aman untuk siswa wirausaha muda.

Flowchart Validasi Transaksi Atomik & Penguncian Stok

Mekanisme penanganan konkurensi database (Row-Level Locking) pada checkout COD untuk mencegah overselling.

flowchart TD
    Start([Mulai: Siswa Menekan 'Konfirmasi Pesanan']) --> OpenRPC[Panggil Stored Procedure / RPC: submit_cod_order]
    OpenRPC --> BeginTx[(Mulai Transaksi Database: BEGIN TRANSACTION)]
    BeginTx --> LockRow["Kunci Baris Produk: SELECT stock FROM market_posts WHERE id = :post_id FOR UPDATE"]
    LockRow --> CheckStock{Apakah Stok Tersedia? (stock > 0)}
    CheckStock -- Tidak (Stok 0 / Terjual) --> RollbackTx[(Batalkan Transaksi: ROLLBACK)]
    RollbackTx --> ReturnError[Kembalikan Error: 'Stok Habis Dibeli Siswa Lain']
    ReturnError --> ShowAlertUI[UI Menampilkan Peringatan & Kembalikan ke Katalog] --> EndFail([Selesai: Transaksi Dibatalkan])
    CheckStock -- Ya (Stok >= 1) --> InsertOrder[(Insert Data Pesanan Baru ke Tabel orders)]
    InsertOrder --> DeductStock[(Update: Kurangi Stok market_posts SET stock = stock - 1)]
    DeductStock --> CommitTx[(Simpan Permanen: COMMIT TRANSACTION)]
    CommitTx --> TriggerEvent[Kirim Sinyal Realtime / Push Notifikasi ke Penjual]
    TriggerEvent --> GenerateReceipt[Terbitkan Kode Transaksi & Nota Digital COD]
    GenerateReceipt --> ShowSuccessUI[UI Menampilkan Modal Sukses & Panduan Titik Temu] --> EndSuccess([Selesai: Pesanan Menunggu Pertemuan COD])

Prinsip Keamanan Transaksi Database (ACID Invariants):

  • Atomicity (Keutuhan): Pengurangan stok pada market_posts dan pembuatan record baru pada orders dieksekusi dalam satu transaksi tunggal. Kegagalan pada salah satu tahap memicu ROLLBACK penuh.
  • Isolation via Row Lock: Klausa SELECT ... FOR UPDATE menahan pembeli lain yang mencoba membeli produk yang sama hingga transaksi pertama selesai (selang waktu < 50ms).

Flowchart Validasi Akun NIS Dua Lapis (Two-Tier Auth)

Alur verifikasi identitas resmi siswa terhadap buku induk sekolah dan proteksi login ganda.

flowchart TD
    Start([Mulai: Registrasi / Login Siswa]) --> InputNIS[Input Nomor Induk Siswa & Password]
    InputNIS --> CheckFormat{Format NIS Angka 4-5 Digit?}
    CheckFormat -- Tidak --> ErrorFormat[Tampilkan Pesan: 'Format NIS Tidak Sesuai'] --> InputNIS
    CheckFormat -- Ya --> QueryRegistry[(Query ke Tabel student_registry)]
    QueryRegistry --> CheckNISExist{NIS Ada di Buku Induk SMKN 8?}
    CheckNISExist -- Tidak Ada --> RejectRegistry[Tolak: 'Bukan Siswa SMKN 8 Semarang'] --> InputNIS
    CheckNISExist -- Ada --> CheckIsActive{Status Siswa Aktif? is_active = true}
    CheckIsActive -- Tidak (Alumni/Pindah) --> RejectInactive[Tolak: 'Status Siswa Tidak Aktif'] --> InputNIS
    CheckIsActive -- Ya --> CheckUserAccount{Sudah Terdaftar di Tabel profiles?}
    
    CheckUserAccount -- Sudah (Alur Login) --> VerifyPass[Validasi Hash Password Supabase Auth]
    VerifyPass --> CheckPassValid{Password Cocok?}
    CheckPassValid -- Salah --> ErrorPass[Tampilkan: 'Password Salah'] --> InputNIS
    CheckPassValid -- Benar --> IssueToken[Terbitkan JWT Session & Bind Device] --> OpenApp([Buka Layar Utama Beranda])
    
    CheckUserAccount -- Belum (Alur Registrasi) --> CreateAuthUser[(Buat Akun Supabase Auth auth.users)]
    CreateAuthUser --> InsertProfile[(Insert Record ke Tabel profiles Terkait NIS)]
    InsertProfile --> IssueToken

Manfaat Arsitektur Two-Tier Auth:

  • Zero Fake Accounts: Mencegah pihak luar mendaftar karena setiap akun wajib terikat dengan 1 nomor induk siswa resmi di SMKN 8 Semarang.
  • Automated Profile Normalization: Nama lengkap, rombel kelas, dan jurusan diambil langsung dari buku induk, mengeliminasi kesalahan ejaan nama siswa.

Keamanan

Spesifikasi Backend & Row Level Security (RLS) Invariants

Aturan isolasi data di PostgreSQL untuk mencegah akses ilegal antar siswa.

Invarian Keamanan Data (Security Invariants):

  • Pemisahan Kepemilikan Produk: Siswa hanya dapat mengedit atau menghapus record pada market_posts jika seller_id = auth.uid().
  • Kerahasiaan Transaksi COD: Record pada tabel orders hanya dapat dibaca oleh pembeli (buyer_id = auth.uid()) atau penjual (seller_id = auth.uid()). Pihak ketiga tidak memiliki hak akses baca.
  • Integritas Buku Induk: Tabel student_registry berstatus Read-Only untuk siswa dan hanya dapat dimodifikasi oleh akun bertaraf admin.
-- Kebijakan RLS Kerahasiaan Pesanan COD
ALTER TABLE public.orders ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Pengguna hanya dapat melihat pesanan terkait dirinya"
ON public.orders
FOR SELECT
TO authenticated
USING (
    buyer_id = auth.uid() OR seller_id = auth.uid()
);

CREATE POLICY "Siswa pembeli dapat membuat pesanan baru"
ON public.orders
FOR INSERT
TO authenticated
WITH CHECK (
    buyer_id = auth.uid()
);

Overview Aplikasi & Arsitektur Interaksi Pengguna (PWA)

Konsep 2-in-1 Social Threads & Vokasi Marketplace, user persona matrix, dan standar rekayasa taktil 120 FPS.

1. Visi Produk Ekosistem sNaps:

sNaps menggabungkan dua pilar utama dalam satu Progressive Web App (PWA) mobile:

  • Ekonomi Kreatif (Marketplace Vokasi): Wadah komersialisasi karya kejuruan (aplikasi PPLG, stiker DKV, makanan Kuliner, dsb) serta sirkulasi buku/seragam preloved di sekolah.
  • Komunikasi & Utas (Threads-Style Social Forum): Ruang interaksi komunitas sekolah untuk mendiskusikan tugas, bug koding, info magang, dan polling voting.

Struktur panduan pengujian saat demonstrasi tugas ujian akhir atau presentasi project-based learning (PJBL).
